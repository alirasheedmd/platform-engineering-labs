# Live ingress reproducibility check: 2026-09-17

Target: the existing two-node DigitalOcean lab. No local Docker environment was
used, no cloud infrastructure was destroyed, and no release deployment was run.

## Changes exercised

Ran `services.yml`, `ingress.yml` and `verify.yml` through the manager using the
existing deployment SSH key. The application service needed no changes. Ingress
adopted the original certificate/key, created managed Docker Configs and a Secret,
and rolled out the updated references and key permissions.

The first ingress run reported `changed=8`, `failed=0`, `unreachable=0`. A second
run of the same playbooks reported `changed=0`, `failed=0`, `unreachable=0`.

## Limits of this evidence

The deployment key authenticates to the manager only. Bootstrap uses the
administrative `id_ed25519` key on both nodes. The initial SSH authentication
failure was resolved by the operator unlocking that key with `ssh-add`; no server
SSH permissions or authorized keys needed changing.

This proves convergence of the private-service and ingress layer on the existing
lab. It does not prove a fresh destroy/rebuild, generation on an empty manager,
certificate renewal, WireGuard recovery, or end-to-end CI after a rebuild. Those
remain explicit gates in the reproducibility runbook.
